# Frostmapper

A static OpenLayers topographic map. Serve this directory with any static web server, for example `python3 -m http.server`, and open localhost:8000. ES modules and map tiles require network access. No build step is required.

The `src/map` directory separates layers, controls, view state, and projection code. `docs` records data sources and design decisions. GitHub Pages serves the repository root directly from the main branch.

The map uses CDN-hosted OpenLayers and proj4js modules. The URL stores latitude, longitude and a projection-independent, Web Mercator-equivalent zoom as `?loc=@latitude,longitude,zoomz`; rotation and projection are stored in the browser. The zoom reflects approximate viewport ground area and can change if the projection's extent forces the viewport to fit. Existing URLs created in another projection before this change used that projection's OpenLayers zoom and may open at a different scale. See [data notes](docs/data.md) for attribution and coverage.

The Peirce picker uses `+proj=peirce_q +lon_0=25 +shape=horizontal`. The registered proj4js extension accepts this horizontal shape with a central longitude; other named shapes are not yet supported. Open `tests/projections.html` on the local server to run the PROJ reference checks.

The Grieger Triptychial option uses the pipeline shown in the PROJ Peirce documentation. Web Mercator and Grieger wrap horizontally, including the national overlays. Their zoom-out limit keeps the viewport filled vertically; shared viewport URLs use the equivalent canonical longitude. Frostmapper accepts `o_type` and `o_scrollx` as aliases for `shape` and `scrollx` in this subset, reproducing the documented horizontal layout. Current PROJ releases accept the original names but ignore them; to reproduce this layout in current PROJ, use `+shape=horizontal +scrollx=-0.25` in the oblique step.

proj4js flattens repeated pipeline tokens, so register raw pipeline strings with `definePipeline(proj4, code, definition)` before passing the resulting named code to proj4js. The supported subset is a pipeline with an oblique Peirce horizontal step defined by `o_lat_p` and `o_lon_p`, and an affine step. This is not a general PROJ pipeline parser.

Reprojected tiles use a source-stitch budget of nine times the output tile area. Source imagery is downscaled while stitching when necessary, keeping OpenLayers’ preferred zoom for ordinary tiles. A separate limit of 32 times the output tile area bounds extreme source footprints; coarser source zooms are used if necessary, and a tile is left empty if none fits. These limits apply per tile, not to total browser memory or the tile caches. The budget hook reuses OpenLayers’ triangulation during synchronous tile construction and relies on the pinned OpenLayers internals; run `tests/reprojection-budget.html` on the local server after changing the OpenLayers version.

Reprojection uses Bézier contours of source/view area distortion, one per doubling of resolution. On first use of a projection, a dedicated web worker generates one source-space contour atlas from the registered projection definitions, through the highest supported source zoom (20). The browser caches it in localStorage under a key containing the target and source PROJ strings. Subsequent visits load that atlas from localStorage. OpenLayers' triangulation supplies the source covering extent for each target tile; a worker plan over that extent chooses the lowest required zoom for a uniform tile, or one zoom higher when bands cross. The same source atlas plans the masks used to assemble mixed-resolution source tiles. Plans arrive in row batches; rendering can use completed rows while planning continues. While no plan is available, OpenLayers uses ordinary reprojection. Tiles with invalid center samples use a nearby valid anchor, and ambiguous plans are split into smaller worker jobs. Contours below the band that maps to the source's maximum zoom are omitted because those bands all use the same highest available source zoom. There is no sampled fallback mask or render-time contour validation. `AssembledZoomTile` fills each requested source-tile extent from masked, upscaled ancestors and downscaled higher-zoom children. At most three adjacent detail levels are used. The source-projection atlas is shared across layers, and each source caches its own parent and assembled tiles. Add `debugBands=1` to the URL to display the source-space bands.

Source-image requests made through the assembler share a concurrency limit of 16 across layers. If a detail image fails, available coarser imagery is retained; if necessary the assembler tries one additional ancestor. A tile can still be missing if every usable source image fails.

The atlas files in `tests/fixtures/contours` are reference fixtures for diagnostics. The app generates its atlases at runtime; `tools/contour-atlas.html` remains available for manual export. `tests/distortion-field.html`, `tests/mask-probe.html` and `tests/contour-integration.html` check sampled field accuracy, band masks and OpenLayers composition respectively. These are diagnostic checks; contour planning runs in the worker and does not sample or validate masks during rendering.

The projection-aware `ProjectionViewport` coordinates switching: it validates the destination, estimates orientation using the inscribed viewport circle, matches approximate ground area, and applies the destination view's extent constraints. When the outer circle is unreliable it blends in smaller circles, eventually falling back to local north. It rechecks area after fitting the view, with a bounded number of passes. The configured projection extent bounds the rotated viewport; this does not guarantee that the underlying tile sources have imagery everywhere inside it. The extent constraint can require a center or area change near an edge. If the original center cannot be represented in the destination, the switch is rejected and the current view is retained. The pre-attachment viewport sizing uses an OpenLayers method tied to the pinned version.

An experimental bounded contour engine and reproducible Grieger comparisons are documented in [the contour ladder notes](docs/contour-ladder.md). The implementation provides global refinement passes, extremum discovery, smooth periodic curves, configurable log₂-step tolerance, and a measured intermediate-memory target below 4 MB. It is available through an opt-in adapter; the current map worker still uses the existing builder.
